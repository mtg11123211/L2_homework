## 1. 图像生命周期与所有权

***解释本项目中图像源为什么会复用缓冲区，以及*** ***`cv::Mat`****的普通复制对底层像素数据*** \
***意味着什么。说明你的修改让一个*** ***`Frame`****在进入队列后拥有什么，并解释为何后续读取*** \
***不会再改变它。***

本项目的图像源用 `buffer_` 成员模拟真实工业相机：相机每次曝光都把新画面写入自己
内部一块固定的内存，而不是每次换一块新内存。代码中对应的是每次 `next()` 都执行
`raw.copyTo(buffer_)`，把新图像覆盖进同一块像素区。

`cv::Mat` 由两部分组成：一个很小的头部(装着指针)和一块较大的在堆上的像素数据。`Mat b = a;` 这样的普通复制只复制头部，两个头部指向同一块
像素，改其中一个的像素，另一个也会看到变化。因此原来的 `frame.image = buffer_;`
让帧和相机缓冲区共享像素，下一帧的 `copyTo` 会把已经入队的旧帧内容覆盖掉，进而导致ctest 返回失败，check.sh 随即中断，后面的 2/3/6 和报告检查都无法进入。

修改为 `frame.image = buffer_.clone();` 后，帧在进入队列时拥有一块属于自己的独立像素（内容与缓冲区完全相同）。此后图像源再次 `copyTo` 只写入缓冲区自己的像素区，
和帧的像素区互不相关，所以后续读取无法再改变这一帧。这处修复让帧完整性测试和流水线测试通过，配合另外两处修复使得 ctest 通过，后续 2/3/6 worker 运行时不会 FAIL: 2 workers saved 0/20 frames（帧不会再被判损坏）。

## 2. 并发处理与恰好一次

***结合*** ***`BlockingQueue`*** ***的*** ***`push`、`pop`*** ***和*** ***`close`****行为，解释多个 worker 如何分工。*** \
***为什么你的实现既不会漏掉已经入队的帧，也不会重复处理同一帧？输入耗尽时，正在等待***\
***以及仍在处理数据的 worker 分别会怎样？***

`BlockingQueue` 靠三样东西让线程之间交接数据：一把互斥锁保证同一时刻只有一个线程操作队列，一个条件变量让空队列上的 worker 等待并在到货时被唤醒，一个关闭标志在队列打烊时通知所有等待者。

`push` 在持有队列锁时把帧放到队尾，然后通知一个等待中的 worker；队列已关闭时直接
返回、不再放入。`pop` 在持有同一把锁时等待“队列非空或已关闭”，条件满足后把队头
元素移动给调用者，并立刻从队列中删除。`close` 设置关闭标志并通知所有等待者。

多个 worker 执行完全相同的循环，靠抢同一把锁分工：谁先抢到锁谁取走队头帧，
锁保证“取出并删除”这一过程不会被其他线程插入，所以同一帧不可能被两个 worker
取走，不会重复处理。每一帧一旦入队就一直留在队列里直到被某次 `pop` 取走；关闭后
等待条件是“已关闭或非空”，worker 仍会先把剩余帧取完，只有队列已空且已关闭时
`pop` 才返回 false，所以已经入队的帧不会被漏掉。

输入耗尽后，正在 `pop` 中等待的 worker 被 `close` 的广播唤醒，加入排空剩余帧的
工作；正在处理帧的 worker 不受影响，保存完当前帧后再次调用 `pop`，等队列排空后
返回 false，线程随即结束。

## 3. 共享统计数据

***指出哪些线程会读写*** ***`Statistics`。解释原实现中的竞争为什么可能导致错误结果，并说明***\
***你的同步方案提供了什么保证。还应说明取得快照时为什么是安全的。***

producer 线程调用 `onProduced`；每个worker线程调用 `onProcessed`、`onSaved` 和
`onCorrupted`；main 线程在结束后通过 `snapshot` 读取全部四个计数。

原实现的自增不是一步完成的，而是“读出旧值、停留一百微秒、写回新值”三步。两个
线程可能同时读到同一个旧值，再分别写回同一个新值，两次计数只生效一次，产生丢失
更新；`snapshot` 不加锁连读四个计数，也可能读到一半新、一半旧的拼凑结果。

同步方案是在 `Statistics` 内设置一把互斥锁，四个计数函数和 `snapshot` 的整个
函数体都在 `lock_guard` 的保护下执行。这样所有“读出、修改、写回”彼此互斥、一次
只允许一个线程进行，计数不会丢失；特意放慢的自增步骤留在锁内，正是为了让互斥
确实覆盖整个读改写过程。取得快照时同一把锁使其他线程无法中途修改任何计数，
返回的四个值来自同一个瞬间。锁声明为 mutable，是因为 `snapshot` 是 const 函数，加锁本身算修改对象，const 函数里要动锁就得这么声明；四个计数器并没有被修改。

## 4. 线程关闭协议

***分别描述以下两条路径中的事件顺序，并解释为什么不会发生*** ***`std::terminate`、悬空访问***\
***或永久等待：***

1. ***调用者执行*** ***`start()`*** ***后显式调用*** ***`wait()`；***
2. ***调用者执行*** ***`start()`*** ***后不调用*** ***`wait()`，直接让*** ***`Pipeline`****析构。***&#x20;

***如果你的实现允许某个生命周期方法被重复调用，也请说明其行为；如果不允许，请说明前置条件。***

关闭协议必须遵守一条铁律：`std::thread` 对象被销毁时，对应线程若仍处于运行中的可连接状态，程序会直接调用 `std::terminate` 终止，因此两条路径都必须在线程结束后才允许对象销毁。

路径一：调用 `start()` 后显式调用 `wait()`。`start` 先启动全部 worker，再启动
producer；producer 把所有帧放入队列后调用 `close`；worker 被唤醒后把队列中的帧
全部处理保存完，`pop` 返回 false，worker 线程结束；`wait` 先 join producer，再逐个 join 全部 worker，全部线程回收后 `wait` 才返回。此后对象析构时没有运行中的
线程，析构函数中的 join 全部因线程不可连接而跳过。

路径二：调用 `start()` 后不调用 `wait()`，对象直接析构。析构函数体先调用
`queue_.close()`，唤醒所有阻塞在 `pop` 上的 worker；随后先 join producer，再
逐个 join worker；worker 把析构时已在队列中的帧处理完后退出。所有线程都在析构
函数体返回前结束，之后成员对象才按声明顺序的逆序析构。

这样就不会调用 `std::terminate`：没有线程还在运行时，线程对象就不会被销毁。线程全部结束后，队列、统计等被它们用到的成员才会析构，所以也不会访问到已经销毁的东西。`close` 在 join 之前执行，所有等待中的 worker 都被唤醒，等待条件里又有已关闭这一分支，join 也不会一直卡住。
关闭的语义是排空式：已入队的帧会被处理完，关闭之后才尝试放入的帧按队列规定被
静默丢弃。

重复调用方面，`wait()` 重复调用也没关系，第二次进来线程都已经不可连接，判断会自动跳过，直接返回；析构函数同理。`start()` 的前置条件是整个生命周期内只调用一次，重复启动会重复创建线程，当前实现不支持这一用法。
